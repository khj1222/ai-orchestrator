# 코딩 에이전트 오케스트레이터가 한 세션에 통째로 맡기는 것보다 나은지 재 봤다

[English](single-session-comparison.md)

결과부터 적는다. 작은 과제 3개에서 숨은 검사를 전부 통과한 실행은 단일 세션 6번 중 6번, 오케스트레이터 9번 중 6번이었다. 실행 시간은 오케스트레이터가 약 2배였다. 미리 정해 둔 규칙으로는 "판정 보류"다.

순수하게 궁금해서 해 본 실험이고, 표본이 작다. 그래도 판정 규칙을 실행 전에 고정하고 작업자에게 주지 않은 검사로 채점했으므로, 과정과 한계를 같이 적어 둔다.

## 무엇을 만들었나

[ai-orchestrator](../README.ko.md)는 개인용 실행 관리자다. 고성능 모델이 과제를 작업 여러 개로 나누어 미리 써 둔 고정 계획을 받아, 그 작업들을 코딩 에이전트 CLI(Codex CLI, Claude Code)에 맡기고, 등록해 둔 검사가 결과 commit에서 모두 통과할 때만 그 작업을 채택해 하나씩 병합한다. 작업자의 "다 했습니다"는 믿지 않고 검사만 본다는 것이 원칙이다.

만들고 나니 당연한 질문이 남았다. 이렇게 나누고 검사하는 것이, 그냥 한 세션에 과제를 통째로 주는 것보다 결과가 나은가?

## 어떻게 쟀나

- **과제 3개.** 각각 규격 문서 하나(210~250줄)로 정의한 작은 Python 라이브러리다. Markdown 부분집합을 HTML로 바꾸는 변환기, CSV 읽기와 스키마 검사 도구, 게임 기록 통계 요약 도구.
- **세 가지 방식.** (1) 단일 세션: 규격을 주고 한 번에 맡긴다. (2) 오케스트레이터, 작업자 1명: 계획대로 작업 3~4개를 차례로. (3) 오케스트레이터, 작업자 2명: 같은 계획을 최대 2개 동시에.
- **실행 15번.** 과제마다 단일 세션 2번, 작업자 1명 1번, 작업자 2명 2번.
- **작업자는 전부 같은 모델.** Codex CLI의 `gpt-6-astra`(high)이고 서브에이전트는 껐다. 계획은 Claude가 과제당 한 번 썼고, 계획이 스스로 꼽은 확인할 점을 내가 검토하고 승인해 고정했다.
- **숨은 검사로 채점.** 과제마다 67~79개 사례다. 작업자에게 주지 않았고, 계획을 쓰는 세션에도 주지 않았다. 한 실행이 "완수"인 것은 숨은 검사를 전부 통과했을 때뿐이다.
- **판정 규칙은 실행 전에 고정.** 오케스트레이터 쪽 완수 비율이 높은 과제가 2개 이상이고 낮은 과제가 없으면 "통한다", 단일 세션이 높은 과제가 2개 이상이면 "안 통한다", 그 밖은 "판정 보류". 병렬은 작업자 1명 조건과 2명 조건이 모두 완수한 과제만 비교하고, 완수하지 못한 실행의 시간은 비교에서 뺀다. 작업자 2명의 벽시계 시간 중앙값이 1명일 때보다 20% 이상 짧아야 이득으로 센다.

## 결과

| 과제 | 단일 세션 | 오케스트레이터(1명 1번 + 2명 2번) | 단일 세션 시간 | 오케스트레이터 시간 |
|---|---|---|---|---|
| Markdown 변환기 | 2/2 완수 | 3/3 완수 | 6~7분 | 14~18분 |
| CSV 검사 도구 | 2/2 완수 | 0/3 완수 (셋 다 74개 중 73개 통과) | 약 4분 | 8~11분 |
| 게임 기록 통계 | 2/2 완수 | 3/3 완수 | 약 5분 | 9~10분 |

- **정확도:** 오케스트레이터가 더 나은 과제는 없었고, 둘은 같았고, 하나는 낮았다. 규칙대로 판정 보류다.
- **시간:** 계획 작성 시간을 빼고도 오케스트레이터의 실행 벽시계는 과제별 평균으로 1.82~2.38배였다. 계획 작성 한 번(과제당 약 18~21분, 기록해 둔 근삿값)과 실행 한 번을 더해 단일 세션의 실행 평균과 견주면 5~7배쯤 된다. 내가 계획을 검토한 시간은 넣지 않았다.
- **토큰:** 과제별 평균으로 견주면 작업자 입력 토큰은 단일 세션의 2.6~4.5배, 출력 토큰은 1.9~2.5배였다. 실행마다 입력의 89~97%는 캐시된 입력이라 요금 배수로 읽으면 안 된다. Codex의 자동 승인 검토가 따로 쓴 토큰은 이 숫자에 들어 있지 않다.
- **병렬:** 20% 기준을 만족한 과제는 비교할 수 있었던 2개 중 0개였다. 두 작업자가 실제로 동시에 돌았고 모든 실행이 완수한 과제는 하나였고, 거기서 17.6% 짧았다.
- 오케스트레이터 실행 9번의 작업 33개는 모두 첫 시도에 채택됐다. 재시도와 통합 실패는 0번이었다.

## 보고 알게 된 것

**단일 세션이 숨은 검사를 전부 통과했다.** 이번 실행에서는 단일 세션이 4~7분에 숨은 검사를 모두 통과해서, 이 완수율 지표로는 오케스트레이터가 더 나아지는 것을 볼 여지가 없었다. 이 실험이 말해 주는 것은 "이번 세 과제에서 이 숨은 검사들을 통과하는 데 분할이 필요하지는 않았다"까지다.

**등록 검사를 다 통과해도 틀릴 수 있다.** CSV 과제에서 오케스트레이터의 세 실행은 등록 검사를 전부 통과하고도 숨은 검사에서 같은 사례 하나를 놓쳤다. 세 실행 모두 한 모듈이 같은 꼴로 그 경우를 빠뜨렸고, 같은 실행의 다른 모듈은 같은 규칙을 더 넓게 검사했다. 계획의 지시문을 보면 그 모듈을 맡은 작업의 지시문이 확인할 경우를 다른 작업의 지시문보다 좁게 열거하고 있었다. 단일 세션 두 번은 계획 없이 규격만 보고 그 경우를 처리했다.

계획의 열거 방식이 영향을 줬을 가능성이 있다. 다만 확인된 것은 아니다. 같은 모델이 같은 지시문에서 같은 해석을 되풀이했을 수도 있고, 한 세션이 과제 전체를 보면서 검증 코드를 한곳에 모은 효과일 수도 있다. 계획이 과제당 하나뿐이라 가를 수 없었다. 확인된 것은 이번에 작업자가 쓴 테스트와 등록 검사가 이 빠짐을 잡지 못했다는 것까지다. 구현과 테스트가 같은 해석을 공유했을 가능성은 있다.

**병렬로 돌 수 있는 것은 계획에서 독립인 작업뿐이다.** 계획 셋 중 하나는 작업이 전부 직렬이라 병렬로 돌릴 것이 없었다. 나머지 둘은 작업 4개 중 앞의 2개만 독립이었다. 두 작업자가 실제로 겹쳐 돈 시간은, 겹침이 있었던 실행 네 번에서 101~135초였다.

## 곁가지로 알게 된 것

**단일 세션 비교군을 만들려면 서브에이전트가 정말 꺼졌는지 확인해야 한다.** Codex CLI 0.163에서 `--disable multi_agent`를 줘도 작업자는 도우미 에이전트를 띄웠다. 게다가 그 생성은 `exec --json` 출력에는 보이지 않고 저장된 세션 기록에만 남았다. 0.164에서 `-c agents.enabled=false`를 주니 막혔다. 버전마다 다시 확인해야 하는 종류의 사실이다.

**다른 회사 모델에게 검토를 맡긴 것이 실제로 틀린 곳을 잡았다.** 결과 보고서와 공개 README 문장은 Claude가 썼고 Codex가 기록에서 숫자를 따로 계산해 검토했다. 판정과 숫자는 일치했는데, 보고서에서 네 군데, README 문장에서 두 군데가 걸렸다. 두 가지만 적는다.

- 초안은 "작업자 실행 시간의 합에서 벽시계 시간을 뺀 값"을 겹쳐 돈 시간이라고 적었다. 벽시계에는 작업자가 돌지 않는 준비·검사·병합 시간이 들어 있으므로 틀린 계산이다. 실제 값은 시작·종료 시각을 교차시켜야 나온다.
- 공개 README 초안의 영어판은 "17.6% faster"라고 적었다. 시간이 17.6% 줄어든 것을 속도로 읽으면 21.3% 빨라진 것이 되고, 그러면 20% 기준을 넘은 것처럼 읽힌다.

## 한계

- 과제 3개, 실행 15번이다. 방향을 볼 수 있을 뿐 통계적 유의성을 말할 수 없다.
- 단일 세션이 전부 완수해서 천장에 붙었다. 한 세션의 문맥이나 시간 상한을 넘는 큰 과제에서 어떻게 되는지는 재지 않았다.
- 계획은 과제당 하나, 작업자 1명 조건은 과제당 1번이다. 계획의 품질 차이와 실행 시간의 변동을 알 수 없다.
- 계획, 작업 분할, 등록 검사, 병렬을 한 묶음으로 단일 세션과 견주었다. 각각의 효과는 따로 가르지 못했다. 재시도는 한 번도 일어나지 않아 그 쓸모도 재지 못했다.
- 완수는 전부 아니면 전무다. CSV 과제의 방향은 74개 중 1개가 정했다.
- 숨은 검사는 Codex가 규격만 보고 썼고 작업자도 Codex다. 계획은 Claude가 썼다. 같은 계열 모델끼리 해석 습관이 맞았을 가능성을 가를 수 없다.
- Codex CLI가 실험 도중에 자동 갱신돼 과제 사이에 버전이 다르다. 한 과제 안에서는 세 방식이 같은 버전이다.
- 과제, 숨은 검사, 실험 도구는 공개하지 않았다. 이 글만으로는 재현할 수 없다.
- 토큰은 세션 기록에 보이는 만큼이고 금액이 아니다.

## 그래서

이번 세 과제에서 단일 세션은 숨은 검사 완수율이 같거나 높았고, 실행 시간이 더 짧았고, 기록된 작업자 토큰도 더 적었다. 오케스트레이터가 쓸모 있으려면 과제가 한 세션에 안 들어갈 만큼 크거나, 정확도가 아닌 다른 이유(서로 다른 모델의 교차 검토, 오래 걸리는 무인 실행, 기록과 감사)가 있어야 할 것 같다. 그쪽은 재지 않았다.

실험은 여기서 닫았다. 도구와 결과, 알려진 한계는 [저장소 README](../README.ko.md)에 있다. 비슷한 것을 재 보신 분이 있다면 결과가 궁금하다.

## 이 실험과 글을 만든 방식

이 프로젝트는 처음부터 코딩 에이전트와 같이 만들었고, 이 실험도 그렇게 했다. 질문과 방향은 내가 정했다. 실험 설계와 실행 관리, 결과 보고서와 이 글의 초안은 Claude Code가 맡았다. 숨은 검사는 Codex가 규격만 보고 썼고, 보고서와 이 글의 숫자도 Codex가 실행 기록에서 다시 계산해 검토했다. 나는 설계와 계획, 실행, 병합을 단계마다 확인하고 승인했다. 그러니 위에서 "내가 했다"고 쓴 일의 상당 부분은 내 승인 아래 에이전트가 한 것이다.
